# Cray MPICH GNU flavors and pinned-GCC compatibility (v1)

| Document control | |
|---|---|
| Date | 2026-07-25 |
| Status | Research note; records evidence for the pinned-GCC decision, nothing here is decided |
| Prompted by | Whether one pinned GCC 12.5.0 can be used on four systems while consuming each system's cray-mpich as an external |
| Method | Primary sources only: HPE CPE documentation, GCC source and release notes, MPICH source, Spack package source. Every claim is labelled as documented by HPE, observed at HPC centers, from GCC, or inference |

## Answer in short

The Fortran risk that motivated this question is smaller than expected, and the
reason is a GCC fact rather than an HPE fact. gfortran stamps `.mod` files with
a format version that changed once between GCC 7 and GCC 8 and then stayed the
same through GCC 14. GCC 12.5 and GCC 13.3 both write and read format `"15"`,
so a `use mpi` or `use mpi_f08` compiled by gfortran 12.5 against `.mod` files
generated by gfortran 13.3 is not rejected on format grounds. The hard cliff is
GCC 15, which bumped the format.

C and C++ were never at risk: `mpi.h` is plain text and `libmpich`/`libmpi_gnu_*`
export a C ABI.

The residual risks are the runtime libraries that come with a Spack-built GCC,
the fact that GCC 12 is end-of-life upstream, and any future CPE release whose
GNU flavor moves to GCC 15 or later.

## 1. The flavor directory convention

### What the path looks like

The install tree is `/opt/cray/pe/mpich/<mpich version>/<netmod>/<compiler
family>/<compiler version>`. HPE's own Spack user documentation shows the
listing and the mapping from Spack compiler spec to prefix
([HPE CPE Spack user documentation](https://cpe.ext.hpe.com/docs/latest/craype/spack.html)):

```yaml
packages:
  cray-mpich:
    buildable: false
    variants: +wrappers
    externals:
    - spec: cray-mpich@8.1.29 %cce
      prefix: /opt/cray/pe/mpich/8.1.29/ofi/cray/17.0
    - spec: cray-mpich@8.1.29 %gcc
      prefix: /opt/cray/pe/mpich/8.1.29/ofi/gnu/12.3
    - spec: cray-mpich@8.1.29 %rocmcc
      prefix: /opt/cray/pe/mpich/8.1.29/ofi/amd/5.0
```

The same page lists the sibling directories under `ofi`: `amd`, `aocc`, `cray`,
`gnu`, `intel`, `man`, `nvidia`, and says each corresponds to a different
compiler for which the MPI library has been built. It instructs the reader to
"ascertain which compiler(s)/hardware-architecture will be used and then find
the corresponding install prefixes for the desired CPE package(s)".

**Documented by HPE.** The trailing component is the compiler version. The
CCE case makes it unambiguous: `%cce` in CPE 24.03/24.07 resolves to
`cray/17.0`, and CCE in that release is 17.0.x. The `%rocmcc` case resolves to
`amd/5.0`. By the same pattern `gnu/12.3` is the GCC 12.3 build.

**Not documented by HPE.** No public HPE page states in prose that the trailing
number is "the GCC major.minor the flavor was built with", nor states the rule
the `cc`/`CC`/`ftn` wrappers use to pick a flavor when the loaded compiler
version does not exactly match a directory. The `ftn` and `intro_mpi` man pages
on cpe.ext.hpe.com do not cover the layout at all
([ftn](https://cpe.ext.hpe.com/docs/24.03/craype/ftn.html),
[intro_mpi](https://cpe.ext.hpe.com/docs/24.03/mpt/mpich/intro_mpi.html)). The
mapping is documented only by example, in the Spack page above.

### Corroborating observations

**Observed at HPC centers and in tooling.**

- `/opt/cray/pe/mpich/8.1.7/ofi/gnu/9.1/include` is where the headers actually
  live, reported against Spack's external handling
  ([spack#25612](https://github.com/spack/spack/issues/25612)).
- `/opt/cray/pe/mpich/8.1.18/ofi/gnu/9.1/lib/libmpi_gnu_91.so.12`, from LUMI's
  CPE training material
  ([LUMI training materials](https://lumi-supercomputer.github.io/LUMI-training-materials/1day-20230509/02_CPE/)).
  The library SONAME encodes the same flavor token, `gnu_91`, so the flavor is
  visible in the link line and not only in the path.
- `/opt/cray/pe/mpich/8.1.28/ofi/cray/17.0/include` and
  `/opt/cray/pe/mpich/9.1.0/ofi/cray/20.0/` at Isambard
  ([Isambard MPI guide](https://docs.isambard.ac.uk/user-documentation/guides/mpi/)).
- Spack's `cray-mpich` package documents the layout in a comment:
  "the GTL are located in /opt/cray/pe/mpich/<cray_mpich_version>/gtl/lib when
  the MPI libraries are in
  /opt/cray/pe/mpich/<cray_mpich_version>/ofi/<vendor>/<vendor_version>"
  ([spack-packages cray_mpich/package.py](https://github.com/spack/spack-packages/blob/develop/repos/spack_repo/builtin/packages/cray_mpich/package.py)).
  The same package resolves an external prefix by reading `CRAY_MPICH_DIR` out
  of `module show cray-mpich/<version>`, which means the flavor Spack picks up
  is whichever one the loaded compiler module selected.

I found no public listing of a `gnu/13.3` directory. That the convention
extends to it is **inference** from the pattern above.

### How this maps to `gcc-native` and `PrgEnv-gnu`

**Documented by HPE.** From CPE 23.12 onward HPE stopped shipping its own GCC.
The CPE 24.07 SLES release announcement states: "Starting with CPE 23.12,
cray-gcc packages will no longer be provided for SLES and COS based systems",
and "Instead, SLES and COS based systems must use SLES-provided gcc*,
gcc*-c++, and gcc*-fortran packages (available from the SLES Development Tools
Module)"
([CPE 24.07 HPCM SLES release announcement](https://cpe.ext.hpe.com/docs/24.07/release_announcements/CPE-24.07-HPCM-SLES-Release-Announcement_Rev.A.html)).
The RHEL equivalent happened at CPE 23.05, with `gcc-toolset` taking over.

**Documented by HPE.** The module that surfaces the OS GCC is `gcc-native`,
and its version is the GCC major.minor. HPE's own worked example shows
`gcc-native/13.0` in the loaded list and the swap message "Lmod is
automatically replacing cce/18.0.1.2 with gcc-native/13.2"
([Swap Programming Environments](https://cpe.ext.hpe.com/docs/latest/craype/swap_prg_env.html)).

**Observed at HPC centers.** OLCF states: "The `gcc-native` compiler module was
introduced in the December 2023 release of the HPE/Cray Programming
Environment (CrayPE) and replaces `gcc`", and that GCC is reached through
either `gcc-native` or the older `gcc` module for versions below 12.3
([Frontier user guide](https://docs.olcf.ornl.gov/systems/frontier_user_guide.html)).
The same guide states that "Cray provides `PrgEnv-<compiler>` modules ... that
load compatible components of a specific compiler toolchain. The components
include the specified compiler as well as MPI, LibSci, and other libraries."

**Observed.** A Perlmutter module list under `cpe/23.12` carries
`gcc-native/12.3` together with `cray-mpich/8.1.28`
([XGC build instructions](https://xgc.pppl.gov/html/cmake_build_instructions.html)),
which matches the `ofi/gnu/12.3` flavor HPE documents for the adjacent
cray-mpich 8.1.29.

**Inference.** `gcc-native/<X.Y>` and `ofi/gnu/<X.Y>` use the same
major.minor key, so on a system with a single GNU flavor the loaded
`gcc-native` version is a reliable read of which flavor the wrappers will
select. The evidence does not support treating the flavor version as an exact
pin: HPE's own example shows `gcc-native/13.2` being loaded in a release whose
documented GNU floor is lower, and `cpe_rocm_compatibility_note_v1.md` already
records the `family_min_version` reading. Treat the directory as a build
baseline.

## 2. What HPE publishes per CPE release

**Documented by HPE, in the public release notes.** Each CPE release notes page
on cpe.ext.hpe.com carries a per-product "supported compilers" list, expressed
as minimum versions. Examples:

| CPE release | Product | Stated GNU support |
|---|---|---|
| 24.07 (RHEL 8.10) | Cray MPICH 8.1.30 | "GNU 11.2 or later" |
| 25.03 (RHEL 9.4) | HPE Cray MPI 8.1.32 | "GNU 11.2 or later" |
| 26.03 (SLES 15 SP6) | HPE Cray MPI 9.1.0 | "GNU 12.3 or later" |
| 26.03 (SLES 15 SP6) | LibSci, HDF5, NetCDF, PnetCDF | "GCC 12.3 or later (SLES)" |

Sources: [CPE 24.07 release notes for RHEL 8.10](https://cpe.ext.hpe.com/docs/24.07/release_notes/index.html),
[CPE 25.03 release notes for RHEL 9.4](https://cpe.ext.hpe.com/docs/latest/release_notes/rhel_9_4_release_notes.html),
[CPE 26.03 release notes for SLES 15 SP6](https://cpe.ext.hpe.com/docs/latest/release_notes/sles_15_6_release_notes.html).

The same release notes name the exact GNU toolchains on RHEL:
"gcc-toolset-10.3/11.2/12.2 (RHEL 8.10)", "gcc-toolset-11.2/12.2/13.1 (RHEL
9.4)", "gcc-toolset-12.2/13.2/14.2 (RHEL 9.5)". Those version numbers are the
same major.minor keys that appear as flavor directories.

**What HPE does not publish publicly.** There is no page that enumerates, per
CPE release, the set of `ofi/gnu/<version>` directories that will exist on
disk. The release notes give a floor ("GNU 11.2 or later"), not a roster.
The CPE 25.09 release announcement points at the "HPE Cray Software
Compatibility Matrixes Reference Guide" (S-8042) for detailed compatibility,
and that document is on the HPE Support Center rather than cpe.ext.hpe.com
([CPE 25.09 CSM release announcement](https://cpe.ext.hpe.com/docs/25.09/release_announcements/CPE-25.09-CSM-Release-Announcement.html)).
So: the floor is public, the exact per-release GNU flavor roster is not, and
the only reliable source for it is `ls` on the target system. The profile
facts listed in `cpe_rocm_compatibility_note_v1.md` should carry it.

## 3. Are the shipped `.mod` files gfortran-version-specific

### Does cray-mpich ship `.mod` files at all

**From MPICH source.** MPICH installs the Fortran module files into the
include directory. `configure.ac` sets `modincdir=$includedir` when it is not
overridden, and the top-level `Makefile.am` sets `modinc_HEADERS =
$(mpi_fc_modules)` under `BUILD_FC_BINDING`. `mpi_fc_modules` is populated by
`src/binding/fortran/use_mpi/Makefile.mk` and
`src/binding/fortran/use_mpi_f08/Makefile.mk` with `mpi.$(MOD)`,
`mpi_f08.$(MOD)`, `mpi_c_interface*.$(MOD)` and the rest
([MPICH configure.ac](https://github.com/pmodels/mpich/blob/main/configure.ac),
[MPICH Makefile.am](https://github.com/pmodels/mpich/blob/main/Makefile.am)).

**Inference.** cray-mpich is HPE's MPICH derivative, and its flavor prefix
contains a full `include` and `lib` pair. Since each flavor is a separate
build with a separate Fortran compiler, each flavor's `include` directory
holds that compiler's own `.mod` files. I found no public directory listing
that shows `mpi.mod` inside a Cray flavor prefix, so confirm this with `ls`
on the first system rather than taking it on trust.

### The gfortran module format version

**From GCC source.** `gcc/fortran/module.cc` defines a single stamp:

```c
/* Don't put any single quote (') in MOD_VERSION, if you want it to be
   recognized.  */
#define MOD_VERSION "15"
```

It is written into the first line of every `.mod`:

```c
gzprintf (module_fp, "GFORTRAN module version '%s' created from %s\n",
          MOD_VERSION, lbasename (gfc_source_file));
```

and checked on read with a plain `strcmp`.

Values across release branches, read from the
[GCC git mirror](https://github.com/gcc-mirror/gcc/blob/releases/gcc-13/gcc/fortran/module.cc):

| GCC series | `MOD_VERSION` | Notes |
|---|---|---|
| 5, 6, 7 | `"14"` | |
| 8, 9, 10, 11, 12, 13, 14 | `"15"` | unchanged for seven majors |
| 15, 16 | `"16"` | plus `#define COMPAT_MOD_VERSIONS { "15" }` |

**From GCC documentation.** The GCC 15 release notes state it directly:

> "The Fortran module `*.mod` format generated by GCC 15 is incompatible with
> the module format generated by GCC 8 - 14, but GCC 15 can for compatibility
> still read GCC 8 - 14 created module files."
> ([GCC 15 changes](https://gcc.gnu.org/gcc-15/changes.html))

### The error messages

**From GCC source**, `gcc/fortran/module.cc`. Version mismatch:

```
Cannot read module file %qs opened at %C, because it was created by a
different version of GNU Fortran
```

Not a gfortran module at all (this is what you get when a Cray `ftn`-generated
module is fed to gfortran, among other cases):

```
File %qs opened at %C is not a GNU Fortran module file
```

Content the reader does not understand, raised through `bad_module`:

```
Reading module %qs at line %d column %d: %s
```

with messages such as `find_enum(): Enum not found`.

### The answer to the question as asked

**From GCC source and documentation.** gfortran 12.5 compiling `use mpi` or
`use mpi_f08` against `.mod` files generated by gfortran 13.3 does **not**
fail the version check. Both stamp `"15"`. Comparing `module.cc` between the
`releases/gcc-12` and `releases/gcc-13` branches shows no module-format change
at all: the only differences are the copyright year and a field rename
(`n->u.linear_op` to `n->u.linear.op`) that does not alter what is written.

**Inference, and the caveat that matters.** A matching stamp is not a formal
guarantee in the new-writes-old-reads direction. GCC 14 added two new module
attribute tokens, `AB_OMP_REQ_MEM_ORDER_ACQUIRE` and
`AB_OMP_REQ_MEM_ORDER_RELEASE`, relative to GCC 13 **without** bumping
`MOD_VERSION`. A module that carries those attributes, meaning one using
`!$omp requires atomic_default_mem_order(acquire|release)`, will be written by
gfortran 14 with the same `"15"` stamp and will then fail in gfortran 13 or
earlier through `find_enum(): Enum not found` rather than through the clean
version-mismatch message. The MPI Fortran bindings do not use that construct,
so this does not affect `mpi.mod` or `mpi_f08.mod`, but it is the reason to
treat "same stamp" as "expected to work, verify once" rather than "guaranteed".

The direction that is safest is old module read by new compiler. The direction
being proposed here, GCC 13.3 modules read by GCC 12.5, is the less safe
direction, and warrants one compile test per system.

**Where it does break.** If any of the four systems ships a GNU flavor built
with GCC 15 or later, gfortran 12.5 will refuse those `.mod` files outright,
with the version-mismatch error above. GCC's compatibility provision runs one
way only: GCC 15 reads GCC 8 to 14 modules, GCC 14 and earlier cannot read GCC
15 modules. On RHEL the highest toolchain HPE names so far is
`gcc-toolset-14.2`, which is still format `"15"`. This is the boundary to
watch in future CPE releases.

## 4. Practical bottom line for a pinned GCC 12.5.0

Scenario: the site pins GCC 12.5.0, and a system's cray-mpich ships only a
`gnu/13.3` flavor.

### C

Works. `mpi.h` is a text header with no compiler-version coupling, and
`libmpich`/`libmpi_gnu_*` export a C ABI. Compiling with GCC 12.5 against a
flavor built by GCC 13.3 is an ordinary C link.

**Documented by HPE, indirectly:** HPE's stated floor for CPE 26.03 is "GNU
12.3 or later", which GCC 12.5.0 satisfies. HPE frames support as a minimum
compiler version, not an exact one.

### C++

Works. MPI removed the C++ bindings in MPI-3, and cray-mpich's C++ support is
`mpi.h` compiled as C++. There is no `.mod` analogue and no C++ ABI surface in
the MPI library itself.

**Inference, and the one thing to watch:** a Spack-built GCC 12.5.0 brings its
own `libstdc++.so.6` and `libgcc_s.so.1`, both older than the system GCC 13.3
runtimes. libstdc++ and libgcc are forward-compatible, not backward: a binary
or library built by GCC 13.3 may reference symbol versions that GCC 12.5's
runtimes do not provide. This is a general hazard of pinning a GCC older than
the system compiler and is not specific to MPI. It bites when a Cray or
third-party shared library in the link closure was built with the newer
toolchain and the pinned GCC's runtime lands first in the RPATH search order.
The mitigation is to resolve the C++ and GCC runtimes to the newer of the two,
not the pinned one. Verify with `ldd` and a symbol-version check on a linked
executable on each system.

### Fortran

Works, on the evidence above, and this is the finding that changes the shape of
the decision. `mpi.mod` and `mpi_f08.mod` generated by gfortran 13.3 carry
format stamp `"15"`, and gfortran 12.5 reads format `"15"`. Neither `use mpi`
nor `use mpi_f08` hits the version check.

Two qualifications:

1. Confirm empirically, once per system, with a two-line program that does
   `use mpi_f08` and `call MPI_Init(...)` compiled by the pinned gfortran
   against the flavor's `include` directory. This is cheap and it is the only
   thing that settles the same-stamp caveat in section 3.
2. `include 'mpif.h'` bypasses `.mod` entirely and is immune to all of this.
   It is not a recommendation, only a fallback worth knowing about.

The failure mode to plan for is not GCC 13.3 today, it is GCC 15 tomorrow. The
day a system's CPE moves its GNU flavor to GCC 15 or later, Fortran against
that flavor stops working with a pinned GCC 12.5 and there is no workaround
short of moving the pin or building our own MPI.

### The other thing the pin has to answer for

**From GCC documentation.** GCC 12.5 was released on 11 July 2025 and the GCC
12 page states "This release series is no longer supported"
([GCC 12 release series](https://gcc.gnu.org/gcc-12/)). Pinning an
end-of-life series means no upstream fix path for a compiler bug found on any
of the four systems. That is a separate argument from MPI compatibility and it
should be weighed on its own.

## What to capture as profile facts

Extending the list already in `cpe_rocm_compatibility_note_v1.md`, per system:

| Fact | How to get it |
|---|---|
| The set of `ofi/gnu/*` flavor directories that exist | `ls /opt/cray/pe/mpich/<ver>/ofi/gnu` |
| Whether `mpi.mod` and `mpi_f08.mod` exist in the chosen flavor's `include` | `ls <prefix>/include/*.mod` |
| The gfortran that wrote them | `head -c 60` on the `.mod` after `gunzip`, which yields the `GFORTRAN module version '<n>'` line |
| The loaded `gcc-native` version | `module list` |
| The CPE release's stated GNU floor | release notes for that CPE version |

The third row is the direct check and it is worth automating in
cluster-inspector: the `.mod` header line is the authoritative statement of
which format version the shipped modules use, and it removes all inference
from this note.
