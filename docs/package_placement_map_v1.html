Reference · lane placement

Package placement map

Every package the curated stack builds, which layer it lives in, and why it lives there. Colours match the lanes-model deck. This is the companion to that deck: it carries the per-package detail the overview leaves out.

How a package's place is decided

Four questions, asked in order. The first one that fits decides the layer.

  1. Does a user link it without ever choosing it? Build tools and stable-ABI low-level libraries are Foundation: one pinned version, reachable through the compiler surface, never a loadable module. Two versions on a fresh compile's link path would be indistinguishable, so there is deliberately only one.
  2. Does no MPI implementation exist for it, and is it compiler-agnostic? Then it is Core: loadable, loads with the compiler surface, before any lane is chosen.
  3. Does no MPI implementation exist, but it must be built with the surface's compiler? Then it is a common compiler-dependent package: built once in the Serial lane, module-visible from every payload lane. It fails the compiler-agnostic test for Core, but has no MPI dimension that would split it per lane.
  4. Is it MPI-capable? Then it is dual-build: ~mpi in Serial, +mpi in MPI and GPU, under the same clean module name. The loaded lane decides which build the name resolves to. A GPU backend on top of that makes it GPU payload.

Settled recently

OpenBLAS is the one BLAS and LAPACK · decided 2026-07-14

netlib-lapack is dropped. OpenBLAS provides both APIs, so nothing loses a capability, and shipping both put LAPACK in the view twice: once inside libopenblas.so, once as liblapack.so. A user linking -llapack would silently get the unoptimized reference build, which is the ambiguity the Foundation pin rule prevents one layer up. Reference LAPACK returns only if a consumer needs it for numerical validation.

ScaLAPACK joins the MPI lane · decided 2026-07-14

Distributed dense linear algebra, built on BLACS over MPI, so it has no serial form and rides the lane's openblas. Two versions, 2.2.3 and 2.2.2.

One TAU, and the GPU lane builds its own · decided 2026-07-14

One version, because a profiler is a tool users run rather than a library their code carries. The GPU lane builds its own tau, with MPI and the GPU backend, rather than reusing the MPI lane's build, which cannot see kernels. The variants are additive, so one GPU-lane build covers MPI, GPU, and MPI+GPU codes; carrying both in that lane would collide on the name tau/2.35.1 and fail loudly.

Open questions

MKL is in CSEinit today, not in this roster

The current flat stack offers MKL. Wheat is an Intel Cascade Lake system, where MKL is the vendor-tuned path. Dropping it silently would be a regression for those users; keeping it is a decision to make on purpose.

Kokkos could serve the CPU lanes too

Kokkos does not link MPI, so it is not an MPI-lane package in the way HDF5 is. It is a portability layer: one build carries a host backend and optionally a device backend, and a GPU build always has both. Today it sits in the GPU lane only, which means a Serial or MPI user has no Kokkos at all. A CPU build could sit in those lanes under the same name, the way Boost's two builds do, which would extend the dual-build rule from the MPI boundary to the GPU boundary.

Deferred for now, deliberately. Kokkos is in the roster to prove the GPU toolchain rather than to serve a request, and the reason to give CPU users a portability layer is performance, which this pass does not chase: everything builds at the portable baseline. Worth revisiting when target optimization turns on, or sooner if someone asks for Kokkos on CPU.

Vendor math libraries alongside OpenBLAS

On Blueback and Fran the PrgEnv already puts cray-libsci on the path, and we declare it consumable, so those users can reach two BLAS. LibSci and MKL are tuned per platform and both carry ScaLAPACK as well. The trade is real: OpenBLAS everywhere means users get the same library on every system and one set of instructions, while vendor libraries are faster on the machine they ship with. Neither is built from source; both are registered as externals, so this is a policy choice per system rather than a build cost.

AMD-tuned libraries, later

Three of the four pilot systems are AMD EPYC, where AOCL (BLIS plus libFLAME) is the vendor-tuned option. This is the same class of decision as CPU target optimization, which this pass deliberately defers: everything builds at the portable baseline first.

Versions are pinned against a single declared Spack package-recipe release, so the whole roster moves together rather than drifting package by package. Updated 2026-07-14.
