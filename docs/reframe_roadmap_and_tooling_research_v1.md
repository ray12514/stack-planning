# ReFrame roadmap and standalone trial tooling research

**Research date:** 2026-10-09  
**Scope:** ReFrame release state, public project direction, and remaining additions for the standalone FFTW/HDF5/LAPACK compiler-hardening campaign described in [`docs/standalone-hardening`](standalone-hardening/README.md).

## Release state and existing history

ReFrame 4.10.4 is the latest stable release at the research date: the official GitHub latest-release API names tag `v4.10.4` with a September 25, 2026 publication date, and PyPI reports package version 4.10.4. This matches the trial's exact pin. [GitHub latest release API](https://api.github.com/repos/reframe-hpc/reframe/releases/latest) · [PyPI package metadata](https://pypi.org/pypi/reframe-hpc/json) · [4.10.4 release page](https://github.com/reframe-hpc/reframe/releases/tag/v4.10.4)

Performance measurement is an established ReFrame capability, not a proposed new direction. ReFrame 2.13 documentation already describes file-based performance logging for retaining history. The 2.21 guide documents per-system reference values and thresholds, a performance report, and the distinction between interactive reporting and long-term logging. Current ReFrame offers performance functions for extracting named measurements, threshold references, JSON run reports, JUnit output, performance logs, and performance query/comparison facilities. Release notes show continued incremental refinement: ReFrame 4.10.0 added multiple aggregations/statistics in performance queries, while recent 4.10 releases continue addressing report and logging details. Thus the trial can use native mechanisms for its test results and comparisons; pairing policy and campaign analysis remain suite-specific. [ReFrame 2.13 manual](https://reframe-hpc.readthedocs.io/_/downloads/en/v2.13/pdf/) · [ReFrame 2.21 run guide](https://reframe-hpc.readthedocs.io/en/v2.21/running.html) · [Current API reference](https://reframe-hpc.readthedocs.io/en/stable/regression_test_api.html) · [Current CLI reference](https://reframe-hpc.readthedocs.io/en/stable/manpage.html) · [4.10.0 release](https://github.com/reframe-hpc/reframe/releases/tag/v4.10.0)

## Public planning signals

I found no standalone maintained roadmap that promises a sequence of future features. Public direction is visible through the GitHub issue tracker, its backlog project, pull requests, and release/sprint milestones. Issue status matters: an open feature request is a request, and milestone assignment indicates intended scope rather than delivery. On the research date, the repository's open milestones included ReFrame 4.10.5 (2 open issues; due October 28, 2026), 4.11 (7 open; due November 11, 2026), and 5.0 (4 open; no due date). These dates are GitHub milestone metadata, not release promises. [Open milestones](https://api.github.com/repos/reframe-hpc/reframe/milestones?state=open) · [ReFrame issues](https://github.com/reframe-hpc/reframe/issues) · [ReFrame organization projects](https://github.com/orgs/reframe-hpc/projects)

The visible 4.11 issue set suggests several concrete themes: faster result storage/querying ([#3638](https://github.com/reframe-hpc/reframe/issues/3638), whose proposal is to shift analytics from Python JSON decoding to database queries); more flexible multi-node resource/distribution controls ([#3491](https://github.com/reframe-hpc/reframe/issues/3491), [#2498](https://github.com/reframe-hpc/reframe/issues/2498)); and refinements to test constraints, environment handling, and scheduler submission behavior ([#3462](https://github.com/reframe-hpc/reframe/issues/3462), [#2910](https://github.com/reframe-hpc/reframe/issues/2910), [#3699](https://github.com/reframe-hpc/reframe/issues/3699)). These tracked issues are not a committed product roadmap.

A concrete reporting example is [issue #3730](https://github.com/reframe-hpc/reframe/issues/3730), opened September 11, 2026, attached to the ReFrame 4.10.4 milestone, and closed September 29 as completed. It described a JSON serialization edge case involving `None` dictionary keys when restoring a session. Treat this as a resolved defect, not current open work. Review release notes and reporting issues/PRs when upgrading, especially for JSON/JUnit consumers. [Open pull requests](https://github.com/reframe-hpc/reframe/pulls)

## Incremental recommendations for the current campaign

The experiment is a standalone direct-source GCC 12.5.0 trial outside Spack, defined in [`docs/standalone-hardening`](standalone-hardening/README.md). Its ReFrame driver already runs the paired harness, which alternates full and comparator arms, uses ten independent timing pairs in the pilot, bootstraps a 95% interval, checks workload correctness, records metadata and raw outputs, and reports geometric-mean runtimes. The Slurm campaign plan also includes a broad predeclared workload/node-count matrix, campaign/run labels, allocation placement checks, and CSV collection. These existing pieces should remain the baseline; the following close residual gaps rather than reintroducing them.

1. **Gate campaign completeness against an expected matrix.** The current collector deliberately includes completed summaries and warns that missing rows are not zero overhead. Add a final check that compares required package × workload × comparator × phase × node/rank cells with collected records, and marks the campaign incomplete when a required cell is absent, duplicated, skipped unexpectedly, or failed. Preserve explicit not-applicable cases (such as LAPACK controls that do not apply) with reasons.
2. **Bind every result to immutable build identities.** Current records capture run context and loaded-library evidence. Ensure the durable summary contains a canonical identity for each full/reference/control artifact: source archive digest or commit, configure/build command and flags, compiler and linker versions, binary/library hashes, and the resolved loaded paths. This lets an analyst distinguish two builds carrying the same human-readable profile label. Record the identity once in a campaign manifest and reference it from each run.
3. **Protect against invalid cross-campaign baselines.** Paired arms control local timing conditions, but comparisons across separate allocations or campaign dates need a guard. Before joining campaigns, require matching workload parameters, CPU target, compiler/build identity, node class, library/runtime versions, filesystem and I/O placement, launcher/transport, and measurement mode; otherwise label the comparison non-comparable. Retain within-campaign pairing as the primary estimate.
4. **Replicate across independent allocations.** Ten paired observations inside one allocation estimate within-allocation variation. Add an agreed number of separately scheduled allocations for a small sentinel subset first, then estimate between-allocation stability. Do not silently pool samples across allocations as if they were exchangeable; retain allocation as a grouping/block in the result model.
5. **Report effect size and uncertainty together.** The current bootstrap interval and geometric-mean ratio are appropriate established outputs. For campaign summaries, retain the point effect and interval, show paired sample count, and classify a predeclared tolerance as below, above, or inconclusive based on interval relation. Keep geometric means consistent with current summaries; do not replace them with medians. Avoid declaring a negligible or acceptable cost solely because an interval includes zero or because an aggregate hides a workload-specific increase.
6. **Produce a portable shareable campaign snapshot.** The runbooks already preserve JSON reports, CSV, logs, and metadata. A lightweight export step could package the campaign manifest, completeness result, per-workload paired estimates/intervals, ReFrame version, and references to raw evidence into one immutable JSON plus concise HTML/Markdown summary. Keep charts optional and generated from that snapshot so a recipient can inspect the result without the live trial filesystem. This is trial-owned integration, not a claim that ReFrame lacks its own reports.

## Contribution direction and boundaries

Keep paired analysis, campaign completeness, artifact identity, cross-campaign comparability rules, allocation replication, and shareable snapshots in the standalone trial tooling unless a minimal reproducer demonstrates a framework defect. ReFrame already supports core metric extraction, performance references, run reports and JUnit export; prefer those supported surfaces before proposing an upstream feature. For a genuine ReFrame issue, provide a reduced check/configuration, pinned version, expected versus actual behavior, and the smallest relevant report/log artifact; search existing issues and follow the repository's contribution information. The repository's README describes ReFrame as a portable regression and benchmark framework and welcomes contributions. [ReFrame repository and contribution section](https://github.com/reframe-hpc/reframe#contributing)

| Boundary | Examples |
|---|---|
| ReFrame provides | Performance functions and references; JSON/JUnit reports; logging handlers; performance queries, aggregations and comparisons. |
| Existing standalone trial tooling | Paired alternating arms; ten-pair pilot and bootstrap interval; correctness checks; metadata and raw CSV/log capture; campaign matrix and scheduler collection. |
| Incremental trial additions | Expected-matrix completeness gate; immutable build identity; cross-campaign comparability guard; independent-allocation replication; interval-based interpretation; portable snapshot export. |
| Possible upstream issue only with evidence | A reproducible 4.10.4 defect in a native report/query/export surface that cannot be handled by trial-side validation or transformation. No upstream commitment for the suggested additions was found. |
