## What ReFrame records and can query

ReFrame has three relevant output paths. First, each run can produce a detailed JSON report; `--report-file` selects its location, and `session_info.version` plus `session_info.data_version` should be retained with any parser because the report schema and test variables evolve. Second, performance tests append configurable CSV-style records to per-test logs under `perflogs/<system>/<partition>/<test>.log`. Third, when result storage is enabled (`RFM_ENABLE_RESULTS_STORAGE=y`), ReFrame stores session/report information in SQLite and supplies commands to list and describe stored sessions/testcases and compare performance across sessions or time ranges. Historical comparison supports selecting sessions or periods and aggregations such as mean/median; it is useful for same-test baseline comparisons, not a ready-made report for the campaign's paired bootstrap estimates. [ReFrame 4.10 tutorial: reporting, performance logging, and historical results](https://reframe-hpc.readthedocs.io/en/v4.10.0/tutorial.html), [ReFrame 4.10 stable command reference](https://reframe-hpc.readthedocs.io/en/stable/manpage.html).

SQLite is the only documented results-storage backend. ReFrame documents file locking for concurrent database access and warns that filesystems without locking support can hang at session end; locate the database on a locking-capable filesystem. You can disable separate JSON file reports when using the DB, but the trial's explicit per-run report files remain valuable portable evidence. ReFrame describes the SQLite contents as essentially the run-report information; it is not a general-purpose campaign warehouse or a plotting/dashboard layer. [ReFrame stable command reference, “Result storage”](https://reframe-hpc.readthedocs.io/en/stable/manpage.html).

For the current campaign, keep `report.json`, console output, run/session identity, and the produced `phases.csv` together as designed in `docs/standalone-hardening/08-slurm-campaign.md`. Use `phases.csv` for the paired full-versus-reference runtime percentage and bootstrap 95% interval: ReFrame's built-in comparisons summarize performance variables across selected history, whereas the campaign collector defines the paired estimate and its uncertainty. Preserve run/campaign, package, workload, comparator, scope, phase, node/rank layout, pair count, and primary/exploratory classification as filters or facets. Treat the full-v-reference primary phase as the headline; removal/PIE comparisons as descriptive attribution. Plot full runtime increase (%) with interval bars and a zero reference, and facet/small-multiple by workload or package. Keep scale (nodes/ranks) separate instead of averaging scales together. For repeated campaigns, plot one point per campaign with campaign date/ID and interval; avoid implying a trend across non-matching workloads or scales.

## Built-in integrations versus dashboards

The ReFrame tutorial documents an `httpjson` performance-log handler that POSTs records to an HTTP endpoint, including an Elastic example and a customizable JSON formatter. This is a transport hook; it does not supply the receiver, storage schema, dashboard, or query API. Tutorial configuration examples include `debug=True`, which writes a sample JSON record rather than sending it, useful for inspecting payload shape before integration. Keep the report version and trial context in the payload or a sidecar manifest, and map the campaign's extra fields explicitly. [ReFrame 4.10 tutorial, “Sending performance data to an HTTP endpoint”](https://reframe-hpc.readthedocs.io/en/v4.10.0/tutorial.html).

There is first-hand evidence of an Elastic/Kibana presentation pattern: the ReFrame team's SC'19 talk describes performance records going to Elasticsearch and appearing on Kibana dashboards in real time. This establishes a documented example, not how common that architecture is today. Grafana could be used separately with a suitable data source, but the ReFrame tutorial does not ship a Grafana dashboard or document a built-in Grafana integration. The tutorial gives Elastic as an HTTP JSON example but does not prescribe a REST API. The docs mention HTTP ingestion, not an HTTP REST interface for querying stored result history. [ReFrame team SC'19 presentation](https://hust-workshop.github.io/2019_presentations/3-reframe.pdf), [ReFrame 4.10 tutorial](https://reframe-hpc.readthedocs.io/en/v4.10.0/tutorial.html).

## Practical choice for these trials

For a simple, reviewable presentation, generate static plots directly from `phases.csv` (and optionally a concise summary table) after collection. That preserves the agreed paired/bootstrap method, gives readable error bars, and avoids introducing a service to support a finite trial. Keep the raw ReFrame JSON and run context adjacent so a plotted point can be traced back to test/session evidence. Enable SQLite only if operators want repeated ReFrame-native historical queries across later runs; it complements but does not replace the campaign CSV or paired-analysis collector. Consider HTTP JSON plus Elastic/Grafana only if the goal becomes live cross-campaign monitoring and a receiver/index/dashboard is already maintained. Version any custom parser or dashboard mapping against ReFrame's report data version, and version the `phases.csv` contract separately.
